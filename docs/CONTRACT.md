# The contract (contract-v1)

The NotTennaPod wire contract: canonical JSON, identity derivations, URL normalization, queue keys, causal order, time normalization and the hashes, digests and MACs every implementation must reproduce byte for byte. The normative text is [PROTOCOL.md](PROTOCOL.md); the `contract/` directory holds the executable definition, and [Import vectors](#import-vectors-android-database-backups) below describes the Android import vectors.

- `contract/vectors/` — shared test vectors, generated by `go run ./cmd/contract-vectors` and checked in, except the rule vectors and `queue_sort.json`, which come from the Python reference (`selftest_rules.py --write contract/vectors` writes `rules_selftest.json` and `queue_sort.json`; `gen_rule_cases.py` writes random rule cases). Every implementation (Go server, Python reference, Swift, Kotlin, TypeScript) must reproduce every vector.
- `contract/reference/` — an independent Python 3 (standard library only) implementation, written from the protocol without reading the Go code. `make check` runs it against `contract/vectors/` and against 10,000 randomized cases generated by the Go implementation.

## Vector file format

Each file is one JSON object: `{"suite": <name>, "cases": [case…]}`. All integers are within ±(2^53−1); bytes are lowercase hex; queue keys use their wire form `q1:<n>:<m hex>`. A case either has an expected result or `"error": true` (the input must be rejected). Suites and their case shapes:

| Suite (file) | Case |
| --- | --- |
| `canonical_json` | `{"input": "<raw JSON text>", "output": "<canonical JSON text>"}` or `{"input": "…", "error": true}` (strict decoding, PROTOCOL §3.1, then JCS). Inputs that are not valid UTF-8 use `"input_hex": "<hex of the raw bytes>"` instead of `input`. |
| `url` | `{"input": "<url>", "output": "<normalized url>"}` |
| `guid` | `{"input": "<raw guid>", "output": "<trimmed>"}` or `{"input": "…", "output": null}` when the GUID is absent |
| `length_prefixed` | `{"fields": ["…"], "output": "<hex of L(fields)>"}` |
| `ids` | `{"kind": "podcast", "namespace", "op_id", "output"}`, `{"kind": "generation", "namespace", "podcast_id", "op_id", "output"}`, `{"kind": "episode", "namespace", "podcast_id", "k", "v", "output"}`; an episode case with an unknown `k` has `"error": true` |
| `queue_parse` | `{"input": "<wire key>", "valid": true \| false}` |
| `queue_compare` | `{"a": "<key>", "b": "<key>", "output": -1 \| 0 \| 1}` |
| `queue_between` | `{"low": "<key>" \| null, "high": "<key>" \| null, "u": "<32 hex>", "output": "<key>"}` (null = sentinel 0 or 1) or `"error": true` when `low >= high` or the key would exceed the exponent bound |
| `causal_order` | `{"nodes": [{"id", "dependencies": [...], "normalized_time"}], "output": [ids…]}` or `{"nodes": …, "error": "dependency_missing" \| "cycle" \| "duplicate"}` |
| `time_normalization` | `{"client_time", "receive_time", "dependency_times": [...], "output"}` |
| `content_hash` | `{"fact": {…}, "output": "<hex>"}` |
| `mac` | `{"key": "<hex>", "account_id": "<uuid>", "object": {…}, "output": "<hex>"}` (the object has no `mac` member) |
| `digest_chain` | `{"previous": "<hex>", "object": {…}, "output": "<hex>"}`; one rule serves commits and snapshot items |
| `cursor` | `{"cursor": {"log_id", "epoch", "seq", "digest"}, "encoded": "<base64url>"}` or `{"encoded": "…", "error": true}` |
| `parts` | `{"parts": ["<base64url data>"…], "content_hash": "<hex>", "fact": {…}}` (reassembles to the canonical bytes of `fact`, whose content hash is `content_hash`) or `{"parts": […], "content_hash": "…", "error": true}` |
| `queue_sort` | `{"description", "items": [{"podcast_id", "title"?, "podcast_title"?, "publication_time"?, "duration"?}…], "output": {"<order>": [item indices in sorted order]…}}`: the canonical comparators of PROTOCOL §7.6 for every keep-sorted order (the ten sort-dialog orders except `random`). `items` are in current queue order; an absent member is a missing value (Android's defaults: title `""`, publication time 0, duration 0). Titles compare by Unicode simple lowercase mapping, then code point; sorts are stable; smart shuffle places equally large podcast groups in ascending podcast ID order. Inputs use only characters whose case mappings are stable since Unicode 15.0. |

Some suites contain sequences that build on earlier outputs (for example 100 insertions into the smallest queue gap); each case is still self-contained.

## Rule vectors

Suite `rules` (`contract/vectors/rules_*.json`) checks the projections of PROTOCOL §7 and §8. Each case:

```json
{"account_id": "<uuid>", "namespace": "<uuid>",
 "arrivals": [{"fact": {…}, "receive_time": 0, "normalized_time": 0, "edges": ["<node id>", …], "capabilities": ["queue", …]}, …],
 "expected": {
   "resolutions": {"<op_id>": {"podcast_id": "…", "generation_id": "…", "mode": "created|joined|opened|stale"}},
   "outcomes": {"<op_id>": {"outcome": "applied|superseded|not_applied|rejected", "reason": "…"}},
   "records": [{"entity": "…", "id": "…", "field_group": "…", "value": {…}}, …]}}
```

- `arrivals` are in acceptance order. `normalized_time` and `edges` (the resolved causal frontier) are what admission computed (PROTOCOL §6.4, §6.9), so rule implementations need not recompute them; `capabilities` are the pushing installation's declared capabilities.
- `resolutions` are the `podcast.resolution` decisions made at acceptance; `outcomes` are the receipts' outcomes and reasons at acceptance.
- `records` is the final set of live (non-tombstoned) records after all arrivals, sorted by `(entity, id, field_group)`, with values exactly as in PROTOCOL §4.

### Server decisions

The server's queue decisions (`queue.resolved_add` and `queue.layout`) depend on the server's random choices, so a vector supplies them, the way the replay holds resolutions fixed:

```json
{"fact": {…}, "receive_time": 0, "normalized_time": 0, "edges": […], "capabilities": […],
 "decisions": [
   {"decision_type": "queue.resolved_add", "decision_id": "<uuid>", "epoch": 1, "seq": 7,
    "position_id": "<uuid>", "draw": 2},
   {"decision_type": "queue.layout", "decision_id": "<uuid>", "epoch": 1, "seq": 7,
    "position_ids": ["<uuid>", …]}]}
```

- `decisions` (optional on a fact arrival) lists the server's choices for every decision its acceptance creates, in creation order (a resolved add before the layout that ends the commit). `epoch` and `seq` are the commit revision the decision gets, so its rank `(epoch, seq, decision_id)` is fixed. A commit has one revision: a fact arrival's decisions are at its receipt's `(epoch, seq)`, and a server commit's (a fetch, a `recovery_end`, a recovered identity decision's unification) at the arrival's position `n` in the account's current epoch, after any epoch evidence the arrival carried; any other revision makes the vector malformed. An arrival the reference refuses as malformed takes no position (a vector never holds it). A layout's `position_ids` are the position IDs of the members that get fresh keys, exactly as many as it needs, in its order; a resolved add's `draw` is the index in `[0, queue size]` drawn for the `random` enqueue location and is present only then. Implementations consume the list strictly: a missing, extra or mismatching choice makes the vector malformed. Absent when the acceptance creates no decision.
- A decision's server time is the receive time of the arrival whose acceptance creates it; its `normalized_time` is the maximum of that and its dependencies' normalized times (PROTOCOL §6.1).
- `"recovery": true` on a fact arrival marks a fact uploaded in recovery: it is admitted with its original normalized time and edges, creates no decision, skips the capability checks (PROTOCOL §10.1) and has no entry in `expected.outcomes` (its original receipt stands).
- A decision arrival `{"decision": {decision_id, decision_type, decision_version, dependencies, normalized_time, epoch, seq, subject, inputs, result}}` (a contract-v1 decision without `key_id` and `mac`) is a decision uploaded in recovery: admitted as recorded (its dependencies must be known nodes), never re-decided; decisions with the same `(decision_type, subject)` compete and the smallest rank is effective (layouts never compete: see "Queue replay").
- `expected.decisions` (optional; absent = none) lists the decisions created during the case (not the uploaded ones), sorted by `decision_id`, each as the decision object above.

### Copied installations

Chain positions and effective authors (PROTOCOL §6.10) follow receipt order, so a fact arrival may state its receipt's position:

```json
{"fact": {…}, "receive_time": 0, "normalized_time": 0, "edges": […], "capabilities": […],
 "receipt": {"epoch": 1, "seq": 7, "index": 0}}
```

- Without `receipt`, an arrival's receipt position is `{"epoch": 1, "seq": n, "index": 0}`, `n` being its 1-based position in `arrivals`. A live (non-recovery) arrival must come after every receipt already archived (a new commit); a recovered one keeps its original position, which may be earlier, and then every chain is reinterpreted and the scopes refolded. No two archived facts share a position (positions are ordered by `(epoch, seq, index, op_id)`; see "Recovery").
- A recovered arrival may also state its original receipt's outcome: `"receipt": {"epoch", "seq", "index", "outcome", "reason"?}`. With `outcome: "rejected"` the fact is archived as rejected (its `edges` are its receipt's frontier, its `normalized_time` its receive time); otherwise it is admitted without re-running the session checks, and contributes nothing if the outcome is `not_applied` with `foreign_session`, `session_ordinal_conflict`, `session_sealed` or `session_finalized`. A recovered arrival may precede an archived dependency that is not a causal node (a fork before its rejected head): its `edges` stand.
- `installation.fork` (type_version 1, core) has the payload `{author, head}` and no targets. Session starts may carry `baseline` and checkpoints and ends `save: {id, index, first?, baseline, passive}`; both are optional, and a session without them is a single path (PROTOCOL §8). `measured_duration.installation_id` is the reporting fact's effective author (a derived author is `a1:` + 64 hex).
- Transport framing (PROTOCOL §6.5) is below the rules and is not modelled.

`rules_forks.json` holds 40 random cases in which every account copies at least one library. It is generated by:

```sh
python3 contract/reference/gen_rule_cases.py contract/vectors --cases 40 --seed 6009 --copies --file rules_forks.json
```

`rules_random.json` holds 30 random cases of the default mode, generated by:

```sh
python3 contract/reference/gen_rule_cases.py contract/vectors --cases 30 --seed 30 --file rules_random.json
```

### Switching away (`episode.leave`)

`episode.leave` (type_version 1, core) is an ordinary fact arrival with the payload `{episode, transition_id, reason, position, observed_claim?, completed, threshold_ms, remove_from_queue, history}`. Its effect and outcomes are in PROTOCOL §8.3 and §8.4; the reference's choices are marked `CHOICE` in `contract/reference/rules.py`. `rules_episode_leave.json` holds its hand-written cases (`selftest_rules.py --groups contract/vectors` writes them). `gen_rule_cases.py` mixes leaves into random and recovery cases unless `--no-leave` is given.

### Resume claims

`session.checkpoint` gains `claim` (a strict boolean, default false, may be omitted) and `observed_claim` (a UUID, allowed only with `claim: true`; evidence, never a precondition). A claiming checkpoint is listening activity (`activity: true`) and covers a new non-passive save, so it carries `save` with `save.passive` false and `save.first` present (non-claiming checkpoints and ends keep `save` optional); anything else is `rejected` / `invalid_payload`. Its save must also be new on its writing path (the `previous_op_id` chain back to the session's start, through an applied fork's head): an earlier export of the session on that path with the same save ID, the same or a higher save index, or the ID the claim names as `first` makes it `rejected` / `invalid_payload`, so it never joins the claim set. That check comes after every existing one, which keeps its outcome (`generation_closed`, `session_sealed`, `session_ordinal_conflict`, `foreign_session`), and a failed check grants nothing. A claim belongs to its writing path (PROTOCOL §8.1, §8.5): it joins the family's claim set, every later checkpoint and end on that path writes under it, and a finalization or leave compares its claim with the current claim at its place. A finalization naming the session's start from a path that has claimed means that path's latest claim. `session.end` takes no `claim`. `rules_offline_merges.json` holds the hand-written cases (`selftest_rules.py --groups contract/vectors` writes them from `selftest_claims.py`), each with its values computed by hand in the generating code: scenario 5a's Monday/Tuesday/Wednesday case in three delivery orders, the earlier example, scenario 1a's literal timeline for E and F, an undetected copy's two paths, reset → resume → completion (with and without the claim), stale ends, finalizations and leaves, adoption → finalization, the start-ID alias, the validation outcomes, and a claim re-exporting a save its path already holds (rejected) beside its fresh-save counterpart, on one path and across an undetected copy in both delivery orders (the copy's facts becoming a derived branch at their acceptance in one of them).

### Queue replay

The queue's order is what one device would show had every queue command been made on it in the deterministic order (PROTOCOL §7.6); keys are a materialization the server publishes in `queue.layout` decisions.

**Payloads** (type_version 1). Every placement carries `place`: `{"kind": "start"}`, `{"kind": "end"}` or `{"kind": "after", "after": EpisodeRef}` (the anchor is context: well-formed, never a target, never a reason to fail). A command without it, or with an add's `moves`, is `rejected` / `invalid_payload`.

| Type | Payload | Targets |
| --- | --- | --- |
| `queue.add` | `{members: [placement…] (non-empty, requested order), place}` | the members |
| `queue.restore` | `{members: [placement…], place}` (the saved index resolved at Undo time) | the members |
| `queue.move` | `{episode, key, position_id, place}` | the episode |
| `queue.reorder` (multi-item move) | `{run: [EpisodeRef…] (the complete selected run, in its resulting order), place, members?}`; `members`: the device's sparse key predictions, non-empty when present, one placement per episode, each naming one of the run's EpisodeRefs exactly as the run names it | the run |
| `queue.reorder` (sort dialog) | `{sort: {sort_order, permutation?}, observed: [EpisodeRef…] (possibly empty)}`; `permutation` exactly for `random`, naming the observed episodes once each | the account |
| `session.start.queue_bundle`, `discovery.propose.queue_bundle` | `{key, position_id, place}` | the episode |
| `queue.remove`, `queue.clear` | unchanged | unchanged |

A placement's keys (a run move's `members` included) are the device's predictions: `run` alone moves, and predictions only feed key retention. Placement and sort commands are `applied` whenever one member passes the bulk checks (a sort always); removals and clears keep their outcomes.

**Decisions.** `queue.resolved_add` carries `result.place` (the server's resolution: `end` for back and after-current, `start` for front, a random draw `i` is `start` at 0, else `after` the queue's (i−1)th episode, as `{episode_id, generation_id}`) and `result.values`. A queue `discovery.admission` carries `result.place` and `result.values` too. `queue.layout` (subject `queue`): `inputs: {frontier, mapping_version, policy}`, `result: {members: [{episode_id, generation_id, key, position_id}…]}` (only the in-members whose key changes, in replay order, keys increasing); its `dependencies` and `inputs.frontier` are the account's whole causal frontier, `mapping_version` the number of identity-mapping decisions held (episode and podcast merges, occurrence mappings, GUID changes), `policy` the node that decided the `sorting` register (or null). Layouts never compete; every one is evidence of what was shown.

**Publication rule** (sparse layouts). Every commit ends with it: every live fact's acceptance (transport duplicates commit nothing), every server fetch, every `recovery_end`, and every recovered identity decision's unification commit. An in-member's **published key** is its latest key write in rank order (the original receipt rank `(epoch, seq, index, ID)`; in one commit the fact, then its decisions, then the layout). Key writes: the members a placement step (add, restore, play bundle, filing, resolved add, import) actually places, absent immediately before the step as the replay decides; every member of a move or run move carrying a key (a run move's prediction), out entries too; every member a layout lists, on its exact (episode, generation). Rejected, malformed and session-refused facts and failing members write nothing; device and decision keys route through references and merges. If the published keys give the replay's order (every in-member has one, strictly increasing), nothing is recorded. Otherwise one layout lists only the members whose key changes: the in-members along the first longest increasing run of published keys keep theirs, the others get fresh keys left to right (a member without a key is off the run); its choice comes last in the arrival's `decisions` and supplies exactly as many `position_ids`. A `queue_position` record is the published key, present only for a scope with a membership record; records change only when that key (or the membership) changes. Different recovery request partitions may record different corrective layouts (different keys, the same order); one fixed archive reconstructs its keys exactly.

**Sort values** are recorded by the server and are part of what is compared:
- a live fact's receipt: `expected.sort_values` (optional; absent = none) is `{op_id: [{episode_id, generation_id, values: {title, podcast_id, podcast_title, publication_time, duration}}…]}`, sorted by (episode, generation): a placement (add, restore, play bundle, move, run move) records the values of its members that pass the bulk checks, and an add, restore or bundle also every member of the queue then when keep-sorted is on at its place; a sort command records the queue then. In the replay a move's recorded values become its members' latest placement values (no membership change, no sort);
- a recovered fact's receipt: `receipt.values` in the same form;
- a decision: `result.values` (resolved adds, queue filings, `import.episode`).

**Imports** (PROTOCOL §11.5) are decision arrivals as the server writes them (`import.podcast`, its `podcast.alias`, the podcast's `catalog.refresh` part 0, `import.episode` per episode, then `import.manifest`), the subset the reference models: unplayed or played episodes with their position, favorite and queue entry, no statistics baselines (`import_android.py` is their oracle). A queued `import.episode` adds `queue_index` (the backup's global Queue index) and `values`. The manifest's `result.result.imported` carries the counts `podcasts`, `episodes` and `queue` (required). The import is one replay step at its manifest's place, once every decision those counts call for is present (`podcasts` `import.podcast`, `episodes` `import.episode`, `queue` of them queued): its episodes at the end in global order. Until then no part of the imported queue is placed, whatever the request boundaries; more decisions than the counts is malformed input. Import cases compare only `expected.field_groups` (`["queue_membership", "queue_position"]`): records of other groups are the import's own.

**Hand-written cases.** `rules_queue_replay.json` (`selftest_rules.py --groups contract/vectors` writes it from `selftest_queue_replay.py`) holds the replay's worked examples and cases, each delivery order a case of its own. Informative members beside a case, which implementations do not read: `name`, `expected_order` (titles, the exact order computed by hand), `by_hand` (how), and `arrival_order_exception` on the metadata race's cases and on the moves cases (a metadata correction racing a sort or a placement's recorded values, the documented exception of PROTOCOL §7.6). Further cases: moves as placements (the metadata race extended, a move before the sort carrying the corrected value: [X, Y]; a move after the sort, whose values never flow back: [X, Y, W]), an import recovered over request boundaries (after the headers, between episode decisions, the manifest first; nothing placed until complete), and a run move with sparse predictions. `check_queue_replay.py` runs every case further: the incremental replay (snapshots, rerun from the earliest affected step) against the full replay after every prefix; every causal arrival order as fresh admissions; one fixed archive in random causal orders; recovery of the archive into an empty server with random request splits, half of them inside commits too (never between a recovered fact and the decisions it caused, which a client uploads in one request). At every publication boundary (a live fact, a fetch, a request end, a recovered identity decision's unification commit) it also checks what a phone shows: the membership records' in-members sorted by their published keys are the replay's order; and the sparse layouts: a commit records a layout only when the keys before it did not give the order, the layout lists only members whose key changes, and every position record is its scope's latest key write, changing only with it or its membership. Recovery compares orders across request partitions, keys only within one fixed archive. `--prefix-only` runs the prefix and publication checks alone. A case marked `recovery_exception` (see "Existing vectors") gets only those two.

**Frozen companions.** Besides the generated files (`rules_selftest.json`, `rules_random.json`, `rules_forks.json`, the group files), three frozen files keep the coverage of earlier generated histories, converted to the replay's payloads by a one-off converter that is not kept: `rules_selftest_pre_replay.json` (209 of the 210 cases: in the other, an episode is named only in a retired `moves` entry, so it is no longer registered), `rules_random_pre_replay.json` (30) and `rules_forks_pre_replay.json` (40); they are never regenerated. The hand-kept files with queue content (`rules_queue.json`, `rules_identity.json`, `rules_undetected_restore.json`) are converted the same way. The converter gives each placement the `place` its device would have resolved against the queue the server showed at its acceptance, drops `moves`, turns a `queue.reorder` of placements into a run move (its keys as predictions), retires sort results, keeps every other server choice (decision IDs, position IDs, draws, commit revisions; layouts are drawn from a fixed seed), translates a dependency on a retired sort result to its commit's replacement evidence, and keeps a fact's normalized time through its `client_time` when the retired decision had raised it (one fact in `rules_queue.json`, one in the frozen forks). It checks that every converted case reproduces the original's resolutions, non-queue outcomes, records other than `queue_position`, non-queue decisions and normalized times, and refuses to write otherwise. The frozen companions are checked like every other vector file.

Many old selftest cases are hand-built shortcuts that no device uploads: a fact names a podcast, generation, session or removal that is outside its own causal past (a device can only name what it synced), for example another phone's `podcast.archive` without a dependency on the subscribe that created the podcast. Live acceptance in the case's order is well defined, but other causal orders (a fixed archive replayed, a recovery) may legitimately give other results. `--mark-invalid` gives each such case (48 of the frozen selftests, found by `check_queue_replay.causal_gaps`) an informative `recovery_exception` member with the reason, which implementations do not read; `check_queue_replay.py` then runs only its prefix and publication checks on it, and `--list-invalid FILE…` lists the cases with such gaps. (The generated files show a few too: the generator's deliberate references to podcasts a device did not sync, which pass every check.)

### Catalog, discovery and server fetches

`catalog.observe` and `discovery.propose` (type_version 1, core) are ordinary fact arrivals (PROTOCOL §9.4, §9.5). The server's own fetches are an input stream of two more arrival kinds; like a fact arrival, each is processed at its place in `arrivals`:

```json
{"fetch_start": {"refresh_id": "<uuid>", "podcast_id": "<P>"}}
{"fetch": {"refresh_id": "<uuid>", "podcast_id": "<P>", "outcome": "success",
           "fetch_time": 0, "feed": {…}, "items": [{"occurrence": {"k", "v", …}, "fields": {…}}, …],
           "redirects": [{"status": 301, "location": "<url>"}, …], "moved_to": "<url>" | null,
           "new_feed_url": "<url>" | null, "next_attempt": 0 | null},
 "receive_time": 0, "decisions": […]}
```

- A `fetch_start` captures what the fetch starts under (PROTOCOL §9.6): the podcast's live generation, the node that determines its refresh URL, and the canonical revision of each catalog record of the podcast (the bases its parts will name). The `fetch` with the same `refresh_id` applies the result. A `fetch` without an earlier `fetch_start` starts and applies at its own arrival. One fetch per podcast is pending at a time; every `refresh_id` is used once.
- `outcome` is `success`, `failure` (`{refresh_id, podcast_id, outcome, fetch_time, error: {label, code, detail}, next_attempt?}`) or `re-parse` (`{refresh_id, podcast_id, outcome, reparse_of, feed, items}`, re-parsing the stored response of the podcast's last successful fetch `reparse_of`; it has no `fetch_start`). `redirects`, `moved_to`, `new_feed_url` and `next_attempt` are optional (none, null).
- `fetch_time` is when the fetch succeeded or failed (at most `receive_time`); `receive_time` is the server's now when the result is applied. `feed` and each item's `fields` are the PROTOCOL §4 record values without `revision` and `fetch_time` (the parser's Feed and Item fields). The server strips userinfo from every URL in them, GUIDs included, also from URLs embedded anywhere in text (`rules.strip_userinfo`; its own cases are `strip_userinfo.json`, suite `strip_userinfo`). The rule reads the text with numeric character references and `&commat;`, `&colon;` and `&sol;` decoded, so `&#64;` is an `@`. A URL starts at `scheme://`, or at a scheme-relative `//` at the start of the text or after U+0000–U+0020 (whitespace and control characters, so a GUID's trim cannot uncover a URL), a quotation mark, an apostrophe, `=`, `(`, `<` or `>`. Its authority runs to the first U+0000–U+0020, `/`, `?`, `#`, `<`, `>` or quotation mark, and to the first apostrophe only when the URL starts right after an apostrophe. Its userinfo, everything up to the last `@`, is removed together with the character references it spans. The server derives each item's episode from what it parsed (PROTOCOL §9.7): the occurrence's `k` gives the GUID kind (`atom-id`, else `rss-guid`; `enclosure` for an item without GUID), its `guid` the GUID, the record's `media.url` and `pub_date` the enclosure and date; `v` and the other occurrence members are not used. `redirects` is the redirect trace (every 301 or 308 `location` becomes an alias when unclaimed); `moved_to` is the fetcher's report of a permanent move (the URL Android would switch to); `new_feed_url` is a publisher-declared URL that was itself fetched successfully, and wins over `moved_to` as the new refresh URL. The refresh URL moves (compared normalized) even onto another podcast's alias; the server then merges the two podcasts in the same commit.
- `decisions` lists the server's choices for the decisions the fetch's commit creates, in creation order: its `catalog.refresh` parts, then each `discovery.admission` (in item order), then the `podcast.moved`, and last the `queue.layout` the publication rule records (see "Queue replay"). A fact arrival's `decisions` may hold an admission too. Choices for `catalog.refresh` and `podcast.moved` have only `decision_type`, `decision_id`, `epoch` and `seq`; an admission adds `position_id` (and `draw` for `random`) exactly when the server resolves its queue placement (a proposal without a bundle, or the server's own discovery with the action `queue`); the admissions one fetch queues are resolved in item order, each against the queue that already holds the ones before it. The decisions of a server-originated commit take `index` 0, 1, … in creation order.
- Recovered catalog decisions arrive as decision arrivals like the queue's. Admissions compete per subject `admission:<G>:<E>` (the smallest rank is effective, and only its filing applies).
- A `catalog.refresh` part's result may carry `seen`: the sorted episode IDs of kept items whose server history the fetch changes without a changed record (new to the history, or catalog-only there and now with an enclosure). Only the first part written after the items are derived carries it: part 0, or, when part 0 was written earlier as identity evidence, the first items part; with no changed item a part with `items: []` is written just for it. A fetch whose items are all unchanged and already in the history writes nothing (unless the status is due). A recovered refresh part restores the server history of its items and of its `seen`.
- New records: podcast `metadata` and `refresh_status`, episode `metadata` (not per generation; kept after an unsubscribe) and episode `admission` (per generation). Proposal reasons: `not_subscribed`, `not_playable`, `ineligible`, `already_admitted` after the acceptance checks. An accepted observation's receipt is `applied`; an observation item's or feed record's `base` may be absent or null (no revision held). The decision schemas the reference writes are in `rules.py` (`_check_catalog_decision_body`); they are part of what the cross-check compares.

`gen_rule_cases.py --catalog` mixes device refreshes (observations and proposals), server fetches (started earlier or not, failures, redirects and moves, re-parses) into random cases. Each catalog show uses one GUID kind (`rss-guid` or `atom-id`) and plain derivations only.

### Identity reconciliation

Identity reconciliation (PROTOCOL §9.7) adds no operation and no arrival kind; it changes how references are applied and adds four server decisions, made at fact acceptance or in a fetch's commit and recovered as decision arrivals:

| Decision | Subject | Made |
| --- | --- | --- |
| `episode.guid_change` | `guid:<P>:<guid>` | on a successful fetch, for each one-to-one GUID-change match, before the fetch's parts |
| `episode.merge` | `merge:<from>` | after a GUID-change match whose new item's episode is registered |
| `episode.occurrence_mapping` | `occurrence:<P>:<guid>:<episode>` | when an observation (a device's, or a fetch's item) disputes a GUID: one per release group, the original release first |
| `episode.occurrence_mapping` (an enclosure addition) | `occurrence:<P>:<guid>:<episode>:<enclosure>` | when a dated occurrence of a disputed GUID names an enclosure that the release its date resolves to does not list; result `{episode_id, enclosure}`. It never competes with releases; `identity_rules` lists a release's enclosures, then its additions in rank order |
| `podcast.merge` | `podcast-merge:<source>` | at the end of a fetch's commit, when a 301/308 hop, the move or the fetched new-feed-url lands on another podcast's alias |

- **The episode's podcast check after a podcast merge**: a reference's episode passes the check when its registered podcast and the named podcast are one merge family (the podcast the reference resolves to), so a reference under a merged-away podcast naming the survivor's episode applies whether that episode was registered first or is named first; an episode of a podcast outside the family is `episode_podcast_mismatch`, in the acceptance checks' order. `rules_identity_family.json` (2 cases, from `selftest_rules.py --groups`) holds both orders.
- A fetch's commit holds, in creation order: `catalog.refresh` part 0 first when the fetch makes identity decisions (it is their evidence), then GUID changes and their merges, occurrence mappings (in item order), the other `catalog.refresh` parts, admissions, the `podcast.moved`, the `podcast.merge`, the occurrence mappings found when the source's evidence joins the survivor's, and last the commit's `queue.layout`. An allocated release (`e0:` + UUID) takes its choice from `occurrence_id`; the other identity decisions supply only `decision_type`, `decision_id`, `epoch` and `seq`.
- Every episode reference is applied where it routes at acceptance, before any state check: through podcast merges by its original podcast and generation (a closed source generation answers `generation_closed`; a lifecycle fact naming a joined source generation answers `generation_merged`), then merge redirects, then, for a reference to its occurrence's plain derivation or its disputed GUID's release family, the server's derivation (a lookup alias, or the release its date or enclosure resolves to). The archived fact is unchanged.
- New records: podcast `identity_rules` (`{disputed_guids: [{guid, releases: [{episode_id, publication_time, enclosures}]}], disputed_enclosures, aliases: [{kind, value, episode_id}]}`, present when not empty), the subscription state `merged` (`{state: merged, merged_into}`, the only record of a merged-away podcast) and `merged_into` in a merged episode's `identity`.
- The decision bodies the reference writes are in `rules.py` (`_check_identity_decision_body`).
- Of two admissions filed into one merged episode, the earlier by decision rank `(epoch, seq, decision_id)` files, even when both name one proposal (`rules_admission_merge.json`).

`gen_rule_cases.py --identity` (implies `--catalog`) adds shows that reuse one GUID for releases days apart with rotating enclosures, news bulletins with new GUIDs on one `/latest.mp3`, hosting moves that change every GUID and enclosure, and feeds permanently redirected onto another show's URL; devices derive IDs through the `identity_rules` they synced.

### Recovery

Recovery (PROTOCOL §6.11) is a union: every recovered entry is joined at its original receipt position, and derived state is a function of the archive in receipt order, whatever the upload order. Vectors gain:

```json
{"decision": {…}, "receive_time": 0, "decisions": […]}
{"recovery_end": true, "receive_time": 0, "decisions": […]}
```

- Receipt positions are ordered by `(epoch, seq, index, op_id)`; two archived facts may share `(epoch, seq, index)`. An arrival without `receipt` is at `(epoch, n, 0)` in the account's current epoch (1 until a live receipt names a later one or epoch evidence moves it). A live arrival's receipt is in the current epoch or later and after every archived receipt.
- **Epoch evidence**: a recovered fact's explicit receipt, or a recovered decision, at or above the account's epoch that the archive does not hold (a replacement counts) moves the account to `max(high-water, its epoch) + 1` before it is joined.
- `podcast.alias` (subject `alias:<normalized feed URL>`, dependencies the creating registration, inputs `{}`, result `{podcast_id}`) and `podcast.resolution` (subject and only dependency the registration, inputs `{}`, result `{podcast_id, mode, generation_id?}`) are decision arrivals like the others. A live registration's own are implicit: vectors record no ID for them (`expected.resolutions` stays), and they rank at their commit after any decision of it.
- A recovered registration makes no decision: it takes effect when its `podcast.resolution` arrives, and facts naming its podcast take effect then. `expected.resolutions` holds every registration's effective resolution (made at acceptance, recovered, or made at a request's end).
- A recovered fact already archived with the same content is known when its position is the archived one, a superseded one or later; with an earlier position it **replaces** the provisional receipt (which is kept, so a later upload of it is known): the fact takes the original position, normalized time, edges and outcome and is derived again. An original `rejected` receipt over a provisional node keeps the node and contributes nothing. `expected.outcomes` keeps what the live acceptance answered.
- A later receipt of an archived fact is known, except when the archived receipt is a rejection and the later one admitted the fact (a provisional acceptance after a restore). That receipt is kept as superseded, and the fact becomes a node that contributes nothing, as when the provisional receipt arrived first and the original replaced it. Recovery stays a union in any upload order (`rules_recovery_receipts.json`, three orders).
- A recovered decision's normalized time is not checked against its dependencies'. After an undetected restore a dependency can be a node at a later time: a lost fact pushed again live, whose provisional receipt precedes the original's position and is kept. The decision still follows it in causal order (`rules_undetected_restore.json`).
- A **conflict** (a known op_id with other content, a known decision ID with another decision, an ID used for both) changes nothing.
- A persisted receipt decides as in receipt order: a fact refused as `generation_closed` contributes nothing, and the generation and alias checks of an admitted one follow its receipt.
- `recovery_end` ends an upload request; it is a server commit at the arrival's position. In receipt order, every admitted registration still without a `podcast.resolution` is resolved as a live one would be (provisional, implicit); then equivalent identity decisions are unified; then the publication rule records one `queue.layout` when the published keys do not give the replay's order (so a recovery-only request can end with a layout and nothing else). Recovered layouts are evidence of what was shown and never change the order; their keys are candidates like any other key write.
- **Competition**: decisions with the same `(decision_type, subject)` compete and the smallest rank `(epoch, seq, decision_id)` is effective; only the effective resolution decision contributes. Identity decisions never split: after a recovered identity decision (and at `recovery_end`) the server unifies what a later decision created with the effective one's result by a new merge: `podcast.alias` per URL, `podcast.resolution` per fact (a later one that created or opened elsewhere), `podcast.merge` per source and `episode.merge` per `from` (their targets), `episode.guid_change` per podcast and GUID (its episode). The podcast survivor is the one whose creating decision ranks first. A unification `episode.merge` has inputs `{podcast_id, cause: "recovered", by}` (`by` the effective decision) and both decisions as dependencies; a unification `podcast.merge` has inputs `{source, into, cause: "recovered"}`. Occurrence mappings of one podcast and GUID are the same release when they share an occurrence or each is the other's only release of another commit within 7 days; the later one's episode merges into the earlier one's, and a GUID's releases list each episode once.
- A decision arrival's `decisions` lists the server's choices for the merges it makes (and `receive_time` its server time, by default its normalized time); a `recovery_end`'s lists those for its resolutions, merges and layout, as a fact arrival's do. A recovered identity decision's unification commit ends with the publication rule too.

`gen_rule_cases.py --recovery` generates random cases (any mode) restored at a random commit: the original's first commits, then the lost commits uploaded from two or three replicas' archives (whole commits, a prefix each) in random orders allowed by their dependencies, with duplicates and request boundaries, and sometimes lost facts pushed again live first (provisional receipts, a detected or an undetected restore), always between upload requests, as nothing interleaves a request. When every lost entry is recovered before any live arrival the final records equal the run without a restore, and every order and duplication of one recovered set gives the same records (`selftest_rules.py` checks both).

### Conventions

- **Times and durations are integer milliseconds**: times since the Unix epoch, as Android stores them; durations, positions and played times as Android's `FeedMedia` columns hold them. A time that Android leaves at 0 (never) is `null`.
- **IDs are the source database's row IDs**: `Feeds.id` (`*_feed_id`), `FeedItems.id` (`*_item_id`), `FeedMedia.id` (`*_media_id`), `Queue.id`, `Favorites.id`. Server IDs depend on the account namespace and the import ID and are not in the vectors.
- Lists are in a fixed order (stated below), so the files compare byte for byte after `json.load`.
- All integers are within ±(2^53−1). The open end of Android's filter (`Long.MAX_VALUE`) is `null`.

Each file is a contract vector file ([Vector file format](#vector-file-format)): `{"suite": "import_android", "cases": [case]}` with exactly one case, the object below. `contract/reference/check_vectors.py` walks `contract/vectors/` and must list suite `import_android` as checked by `selftest_import.py`.

| Member | Value |

#### `result`

- `imported`: `{podcasts, episodes, queue, favorites, history, inbox}`: numbers of podcasts, episodes, queued episodes, favorite episodes, episodes with a history time (the episode's `history`) and episodes in the Inbox.
- `skipped`: `[{reason, title, source_feed_id}]` by feed ID; `reason` is `local_folder` (`download_url` starts with `antennapod_local:`), `no_feed_url`, or `unused_preview` (a preview feed, state 1, none of whose rows is played, NEW, favorite or queued or has a position, history, last played or played time; ruling 3). The unused-preview rule applies per feed before URL grouping, so an unused preview never joins another feed's podcast.
- `ambiguous`: `[{reason: "no_guid_no_enclosure", podcast, title, source_item_id}]`, by podcast, then item.
- `merged`: per podcast in podcast order, `{kind: "podcast", title, source_feed_ids}` when several feeds became it, then `{kind: "episode", podcast, title, source_item_ids}` for each episode made of several rows, by first item ID.
- Titles are `custom_title` when non-empty, else `title`; a merged episode's title is its state row's.

#### `podcasts[]`

| Member | Value |
| --- | --- |
| `creating_feed_id` | The lowest feed ID of the group: it creates the podcast. |
| `source_feed_ids` | Every feed whose `download_url` normalizes (contract-v1, userinfo removed) to this podcast's URL, ascending. |
| `properties_feed_id` | The feed whose subscription properties the podcast takes: the lowest-ID non-preview feed of the group, or the lowest-ID feed when all are previews (ruling 2). |
| `title`, `url`, `normalized_url` | The creating feed's title and raw URL (userinfo removed), and the normalized form. |
| `k` | `atom-id` when the creating feed's `type` is `atom`, else `rss-guid`. |
| `state` | `subscribed`, `not_subscribed` (preview) or `archived` (`Feeds.state` 0, 1, 2; NULL is 0; other values `subscribed`). |
| `keep_updated` | `keep_updated > 0` (Android's cursor; NULL is false). |
| `new_episodes_action` | `global`, `inbox`, `nothing`, `queue` for 0, 1, 2, 3; another code `inbox` (`NewEpisodesAction.fromCode`); NULL `global`. |
| `credentials`, `credentials_feed_id` | Whether a sealed secret is expected, and the feed it comes from: the properties feed if it has credentials, else the first feed of the group in ID order that has any (ruling 2), else `null`. A feed has credentials when its username or password is non-empty or its URL has userinfo; URL userinfo is stripped and becomes the secret (ruling 6). Credential values never appear. |
| `populated` | Whether the generation has at least one item (PROTOCOL §11.5: first population). |
| `episodes` | By first source item ID. |

#### `episodes[]`

| Member | Value |
| --- | --- |
| `source_item_ids` | The rows that are this episode, ascending. Each row is a `FeedItems` row with its lowest-id `FeedMedia` row (Android's LEFT JOIN). |
| `identity` | How the episode ID is derived. `{k, v}` with `k` in `rss-guid`, `atom-id`, `rss-guid+enclosure`, `enclosure`: the ID is contract-v1 `episode_id(A, P, k, v)` (`v` for `rss-guid+enclosure` is GUID, U+001F, normalized enclosure). `{k: "e0", reason, source_item_id}`: an `e0:` occurrence ID; for `no_guid_no_enclosure` it is `e0:` + UUIDv5(import ID, that source item ID); for `release_id_taken` (a later release whose `rss-guid+enclosure` ID an earlier release already has, PROTOCOL §9.7) any persisted `e0:` ID. |
| `title` | The state row's title. |
| `state_item_id` | The state row: the greatest `last_played_time` (NULL is 0), then the highest item ID. |
| `play_state` | `played` (`read` 1), `new` (`read` −1) or `unplayed`, from the state row. |
| `inbox` | `play_state == "new"`. |
| `position_ms` | The state row's `FeedMedia.position` as Android's cursor reads it (`getInt`: truncated to a signed 32-bit value), 0 without media. |
| `favorite`, `queued` | Unions over the rows. |
| `duration_ms` | The state row's `FeedMedia.duration` (the measured-duration evidence); `null` without media. |
| `history` | The episode's history time: its state row's own `playback_completion_date` when > 0 (ruling 4, as revised), that is its baseline's `history`; `null` if none. A unit's history stays the unit's, so the History list may miss a merged episode whose only history is in another row. |
| `baseline` | The state row's statistics baseline, `{source_item_id, source_media_id, played_ms, last_played, history}` (`played_duration`, NULL 0; `last_played_time` and the row's own `playback_completion_date` when > 0, else `null`), or `null` when all three are zero or the row has no media. |
| `units` | The other rows' separate statistical units (PROTOCOL §11.5), by item ID: `{source_item_id, source_media_id, played_ms, last_played, history, duration_ms, played, position_ms}` for **every** other row that has a media row, even an all-zero one; rows without a media row make none. `played` is that row's own `read == 1` and `position_ms` its own position (read as `getInt`), frozen. |

Episode grouping inside a podcast (PROTOCOL §3.3, §9.7): rows with a GUID (trimmed; empty and `null` are absent) group by GUID, then into release groups; rows without GUID but with an enclosure group by the normalized enclosure (userinfo removed); rows with neither stay alone. Release groups are built in two passes. First, releases are created in publication-date order (ties by item ID): the first dated row creates one, and a later row creates one when it is more than 7 days from every release's date, has an enclosure, and an earlier row has a different enclosure more than 7 days away; the creating row's date and enclosure are the release's date and first enclosure. Then every row is placed where PROTOCOL §9.7's resolver puts it: a dated row in the release whose date is nearest within 7 days (ties: the earlier release); any other row (dated far from every release, or undated) in the release holding its enclosure if exactly one does, else in the earliest release. A GUID without dated rows is one release. The earliest release keeps the plain ID.

#### `statistics`

- `android`: Android 3.12.1's own SQL run on the file (`PodDBAdapter.getFeedStatisticsCursor` and `getMonthlyStatisticsCursor`, transcribed in `import_android.py`):
  - `per_feed`: one entry per feed Android lists (state != 1, at least one item): `{feed_id, played_ms, played_marked_ms, episodes_started, episodes_started_marked, episodes, total_ms}`. `played_ms` is the default filter `[0, Long.MAX_VALUE)`; the `_marked` values are "include marked as played" (always all-time in Android). Android displays `played_ms / 1000` and `total_ms / 1000` per feed.
  - `per_podcast`: the same summed over each imported podcast's feeds, keyed `creating_feed_id`.
  - `windows`: `[{from, to, per_podcast: [{creating_feed_id, played_ms}]}]`, the played time per podcast with Android's date filter `[from, to)`: the default `[0, ∞)`, `[start of the UTC month of Android's oldest date, ∞)` (`DBReader`'s `oldestDate`; Android's "All time" button) and each UTC calendar month with a positive `last_played_time`.
  - `monthly`: `[{year, month, played_ms}]`, Android's "Years" screen data (UTC months).
- `projection`: the same numbers computed only from `podcasts` (episodes and units) with the client projection of PROTOCOL §8.8: per podcast for `subscribed` and `archived` podcasts, per month for all. Each episode counts once with its baseline's played time and last played, its `history`, its duration, play state and position; each unit counts once with its own values (ruling 1). An absent `last_played` counts as 0 in date filters (the client rule of ruling 7: Android's default filter includes rows whose `last_played_time` is 0). "Include marked as played" uses the played time if non-zero, else the duration if PLAYED. Started means a history time and played time > 0; with "include marked as played" also PLAYED or a position > 0. `episodes` counts episodes plus units. Monthly totals group every positive played total by the UTC month of its positive `last_played`, previews included.
- Differences between `android` and `projection`, in two lists of the same entry shape: `{metric: "per_podcast.<number>", podcast, …}`, `{metric: "window.played_ms", from, to, podcast, …}`, `{metric: "monthly.played_ms", month: "YYYY-MM", …}` or `{metric: "per_feed_not_imported", feed_id, android: {non-zero numbers}, projection: null}` (a feed Android lists that is not imported), each with `android`, `projection` and `causes` (the names of the causes whose adjustment changes it):
  - `expected_differences`: differences the rulings accept. Each disappears when Android's SQL runs on a scratch copy of the file with every detected cause adjusted.
  - `mismatches`: anything else, which would be a reference or design error. Empty for every vector.
- `causes`: the conditions detected in the file, each `{cause, detail, …source IDs}`:
  - `skipped_local_folder`, `skipped_unused_preview`, `skipped_no_feed_url`: a skipped feed's rows (adjusted by deleting them; Android counts local folders per feed and per month; unused previews hold no statistics);
  - `preview_feed_joins_listed_podcast`: a used preview feed whose URL equals a subscribed or archived feed's; Android leaves it out of the per-feed list, the merged podcast counts it (ruling 2; adjusted by listing the feed);
  - `merged_row_without_media`: a merged row without a media row makes no unit; Android counts it as an episode, and as started with "include marked as played" when it is PLAYED (ruling 1; adjusted by deleting it);
  - `absent_last_played_client_rule`: played time with no last-played date (Android's `last_played_time` 0, as rows from before 1.4 have) counts in date filters starting at 0 only through the client rule of ruling 7, never in "All time" or per month. It is a note: under that rule there is no difference (`played_ms` gives the amount);
  - `media_not_imported`, `items_without_feed`, `null_last_played_time`: malformed files.

### Expected differences, per fixture

No vector has a mismatch. The four emulator libraries and `merged-rows` have no expected difference either. `merged-rows` notes `absent_last_played_client_rule` for item 14 (1,200,000 ms counted in the default filter).

- `feeds-lifecycle`: the local folder's listening (120,000 ms in July 2026) is in Android's per-feed list and monthly total, and nowhere after the import (`skipped_local_folder`).
- `parity-gaps`:
  - Podcast 1, row 11 (`zero-dup`, PLAYED, no media row) has no unit. Android counts 11 episodes and 10 started ("include marked as played"); the projection counts 10 and 9 (`merged_row_without_media`).
  - Podcast 2: its used preview feed 3 has the same URL as subscribed feed 2. Its row joins the podcast: played time 1,400,000 against 1,000,000 ms, and every other per-podcast number and window (`preview_feed_joins_listed_podcast`, inherent to the merge).
  - Rows 12–13 (`hist-dup`): the state row 13 was removed from history and row 12 keeps its history. The episode takes row 13's (none), so it is not started, and row 12 counts through its unit: 5 started, as in Android.
  - Rows 1, 3, 5 and 7 are counted through their units (an all-zero row, a PLAYED row with duration 0, a position-only row, a PLAYED row never listened to). Without the unit's `played` flag, row 7's 1,500,000 ms would drop out of the marked-played total; the self-test checks that.

### How a Go test should compare

1. Import the file into an empty account. The test needs the importer's map from source IDs to podcast IDs (per source feed: the `import.podcast` decision) and to episode IDs (per source item), and the baselines' and units' source media IDs.
2. **Podcasts**: the same groups of source feeds; `state`, `keep_updated`, `new_episodes_action` equal; a sealed secret exists exactly when `credentials`, holding `credentials_feed_id`'s username and password (or its URL userinfo); the podcast URL equals `url`; the generation counts as populated exactly when `populated`.
3. **Episodes**: the same partition of each podcast's source items. For `{k, v}` identities, compute the expected ID with contract-v1 `episode_id` from the account namespace and the podcast ID and compare exactly; for `e0` identities, check the kind (an `e0:` ID), and for `no_guid_no_enclosure` the UUIDv5 rule. Play state, Inbox, position, favorite, queue membership and measured duration equal.
4. **Baselines, units and history**: the state row's baseline equals `baseline` (a missing baseline equals an all-zero one); the units are exactly `units`, compared as a set keyed by `source_media_id`, including `played` and `position_ms`; the episode's history time equals `history`.
5. **Queue**: the queue's episodes, front to back, are the episodes of the items in `queue`.
6. **Result**: `imported` counts equal; `skipped`, `ambiguous` and `merged` equal as sets keyed by source IDs, titles included.
7. **Statistics**: the server's statistics projection after the import (read API or client projection, with the client rule that an absent `last_played` is 0 in date filters) equals `statistics.projection` for every podcast, window and month. "Android numbers unchanged" (scenario 24) then holds everywhere except the listed `expected_differences`.
8. A podcast without items has no Android row; it compares as all zeros.
