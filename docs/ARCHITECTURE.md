# Architecture

NotTennaPod-Server is one Go binary (`cmd/nottennapod-server`) with one SQLite database per data directory. It speaks the protocol in [PROTOCOL.md](PROTOCOL.md), refreshes feeds, and serves the web client. The external Go modules it uses directly are the pure-Go SQLite driver `modernc.org/sqlite`, `golang.org/x/crypto` (Argon2) and `golang.org/x/text` (feed encodings); ffmpeg and ffprobe are an optional runtime dependency of the media relay.

## How a request flows

1. `internal/httpserver` accepts the connection, applies read and write deadlines and refuses unknown `Host` names (`421`).
2. `internal/api` matches the route, bounds and decodes the body (the sync bodies strictly, as contract-v1 JSON; the others as typed JSON that refuses unknown members and trailing data, the recovery-key export also refusing invalid UTF-8 and lone surrogate escapes), checks the content type and `Origin`, and resolves the bearer token or the session cookies (one per session) to a principal (account, installation, kind, administrator). Handlers reach data only through that principal's account scope.
3. A **push** (`/v1/push`) goes to `internal/protocol`: in one write transaction it re-validates the credential, checks the lineage, and admits each operation in order (slots, parts, envelope and payload checks, dependencies, normalized time). Each admitted fact is applied by its `internal/ops` handler, which records contributions and creates decisions; `internal/projection` refolds every touched scope; the changed records, the accepted entries, the decisions and the consumed slots become one commit appended by `internal/storage` with the next `seq` and digest. The response lists one result per processed operation.
4. A **pull** reads commits from one read snapshot and pages them with MAC-protected tokens; a **snapshot** materializes a durable view file outside the write lock and pages it.
5. **Server-originated work** (feed refreshes, admissions found by the server, re-parses, import publication) fetches and parses outside any transaction, then commits its decisions through the same store in one short write transaction.
   A **recovery upload** whose derivation outlasts its request goes on as a job in the server's lifetime (`internal/protocol/recovery_jobs.go`): its request is kept, sealed, in `recovery_jobs` (migration `0029`) until the job's commit deletes it, the request is answered `server_busy` with `retry_after` after 20 seconds, and a restart resumes the job (`Service.StartRecoveryJobs`).
6. Every commit notifies `/v1/events` listeners of the account's new head; the web client then re-reads its views from `internal/views`.

All writes are serialized through one writer connection, so `seq` is allocated in commit order and no write transaction does network I/O.

## Queue replay

The queue's order is a replay of the account's queue history (PROTOCOL §7.6). `queue.State` is persistent: its structure (every entry by an internal order-maintenance label), the members in order, the memberships, values and key writes are persistent trees (`internal/views/ptree`), so a snapshot is a copy of a few roots and reading the queue walks only its members. When labels run out at a place, only the smallest aligned label range around it that is sparse enough is relabelled. Each account's snapshots, thinned by age, and its published keys are kept in memory (`ops/queue_replay.go`), valid while the account's head has not moved; a commit replays from the latest snapshot before the earliest node it changed. Its publication then recomputes only the entries whose key write changed since the cached state, and the scopes with layout key writes ranked after the last one the cache saw (`queue_keys_by_rank`); a rebuild, a changed identity or generation mapping, a missing cache or layout writes the replay did not make (a recovered layout) publish in full. After a start, `ops.WarmQueues` replays each account active in the last 30 days (`storage.RecentlyActiveAccounts`) once in the background in a transaction that is rolled back, so the first queue command does not replay the whole history. `internal/queue/replay_reference_test.go` is a frozen copy of the earlier state the persistent one is compared with after every node of long random sequences.

The queue frontier (the queue nodes no other queue node descends from, which a layout depends on) is kept by `AccountTx.AddQueueNode` (`internal/storage/queue_admission.go`). It finds a new queue node's relationships to the frontier by walking the causal graph from the node, a page of a node's edges at a time and never past a frontier node it reaches; a node whose whole past is small, as an imported episode's is, never reads the frontier. Otherwise three searches take turns: the node's walk, a walk from each unresolved frontier node toward it (related when the walks meet, unrelated when either ends), and a sweep of the edges ranked between them in rank order, as the earlier admission read them, which advances 24 edges for each walk query and resolves each frontier node it passes. So a command costs about what relates it to the frontier when that is short, and never much more than one read of the ranks between them when it is not (a history all descending from the frontier node, such as a device's checkpoints since its last queue change, is still read once). `internal/storage/queue_admission_test.go` compares it with the earlier admission after every step of random causal graphs, bounding each admission's walk queries by the ranks between the node and the frontier, and bounds its rows for an import's queue, out-of-rank admission, commands after 100,000 unrelated nodes, small commands after a wide fact and connected histories.

A new node's causal rank is found by two scans taking turns (`insertRank`): the nodes after its last dependency in rank order and the nodes of greater priority, so an old fact reads about the nodes it is placed after, not the archive. The rank is the midpoint of the gap at that place (a node placed last takes the last rank plus 2^20), and a used-up gap renumbers the whole account in rank order at a spacing of 2^20 (`renumber`), exactly the ranks earlier servers gave, so a database one of them wrote rebuilds to the same ranks (`rank_upgrade_test.go` keeps their placement as the oracle). `rank_placement_test.go` bounds the rows read: an offline burst of 300 facts placed before a later history of 2,000 nodes reads at most 4 rows a fact.

## Read-model change capture

The browser's views of an account (`internal/views`) read its *view inputs*: every `records` row, which episodes are registered (`episodes`), each catalog item's publication date and insertion rank (`catalog_items.pub_date`, `rowid`), each podcast's creating node (`podcasts.creating_op`) and that node's causal rank (`node_order.rank`). Migration `0025_read_model_changes.sql` records, in the transaction that makes it, every change to them (`internal/storage/viewchanges.go`):

- `view_clock` holds each account's *tick*, which every change raises, and *generation*, which every bulk rewrite raises. An account without a row is at (0, 0).
- `view_changes` holds each changed entity (`account`, `podcast` or `episode`) once, at the tick of its latest change. `ViewChangesSince` reads those above a tick in exact pages of 1,000 through the covering index `view_changes_by_tick`; `ViewEntityRecords`, `RegisteredEpisodes`, `CatalogRowsFor` and `PodcastRanksFor` read the changed entities by primary key, 500 IDs a statement, as the full readers would.
- Fifteen `view_capture_*` triggers (insert, update and delete on each of the five tables) do it. A statement that changes no view input (an identical upsert, a podcast-only move of an episode or catalog item, another node's rank) stamps nothing.
- The bulk rewrites, `PublishImport`, `PublishStaged`, `AccountTx.ClearDerived` (an in-place rebuild or recovery) and `WriteTx.DeleteAccount`, call `WriteTx.SuspendViewCapture` for their account: the triggers are dropped for the rest of the transaction, so the rewrite costs nothing per row, and before it commits `Store.Write` creates them again from the same text, raises the declared accounts' generation and tick and clears their old stamps (a deleted account keeps neither clock nor stamps), and wakes their listeners. Other accounts are untouched.
- Within a log lineage (account, `log_id`, epoch), (generation, tick) never decreases. `view_clock` and `view_changes` are the live database's own: a rebuild keeps them (`rebuildKept`) and an import never copies them (`importExcluded`). Staging databases keep their triggers, and their clocks are never copied.
- Opening a server's or a staging database whose only difference from its migrations' schema is absent capture triggers creates them again and raises every account's generation, with a warning; any other difference still refuses to start, and a copy (`OpenCopy`) never repairs.
- The server never runs an in-place `VACUUM` (backups use `VACUUM INTO`; `TestNoInPlaceVacuumOrReplaceOfViewInputs`), and never writes a view-input table with `REPLACE`, whose implicit deletes fire no trigger. An in-place vacuum, if one is ever added, must run with the server stopped, or with the writer held outside any transaction, and then raise every account's generation in a write transaction before any read is served.
- Tests turn on `storage.AuditViewCaptureForTesting` in their `TestMain`: TEMP triggers on the writer connection record every view-input change and every change of an account's log or clock, and each transaction checks before it commits that its changes are stamped within its ticks (the tick moving forward) or its accounts declared, that no stamp is above its account's tick, and that no clock went backwards. The audit's triggers refuse a view-input or clock write made outside `Store.Write`, and a write refuses to start over changes no write checked. `storage.ObserveCommitsForTesting` lets a test see each commit with the identity (head, clock) of every account whose view key it changed, while a write gate keeps the next write out, so the store's newest snapshot is the commit's; the writes a store makes while it opens are observed as one commit once it is open.

## Read model

`internal/views` keeps an account's library as a *version* (`model.go`), from which the read API serves: an immutable value whose structures are persistent, path-copying treaps (`internal/views/ptree`; a key's priority hashes the key, so a tree's shape is a function of its entries). It holds each record once, raw, and the scalars its builders decode from them:

- the shown podcasts, the stored episodes (registered, identified, not merged), and each podcast's aggregates over its stored episodes (episodes per filter class, of 96, and its statistics totals);
- the 11 sort orders, keyed by (podcast, class, sort value with SQLite's NULL rules, rank, ID), so a list is a set of (podcast, class) ranges;
- the queue and the Continue partitions, Surprise's candidates and recent plays, keyed by podcast first, so the shown podcasts are chosen when a list is read and showing or hiding a podcast re-keys none of them;
- each statistics part at its own last-played date, played time by UTC month per podcast, and its sum over the shown podcasts.

`BuildVersion` builds a version in full from one snapshot, with the same reads and rules as the oracle's `Load` (`internal/views/reference`). `Version.Apply` makes the version of a later snapshot of the same lineage and generation from every entity stamped above the version's tick (`ViewChangesSince`, page by page, and the changed entities by primary key): each changed episode leaves every structure and enters it again as it now is, at O(log n) a structure, and a podcast that is shown or hidden adds or removes only its own months. Its work is that of the change, never of the library, its queue or its history. Another lineage or generation, or no earlier version, is a full build (`Advance`). `EqualVersions` compares two versions' content: records byte for byte, every field, every structure's entries and aggregates.

Serving (`internal/api/read.go`, `media.go`):

- `views.Cache` (`cache.go`) keeps each account's published version and builds it once for everyone. Every caller (a request, the account's warmer, the startup warm-up, a verification) takes the account's incarnation, then opens a read transaction, has the caller checked again and reads its snapshot's key; under the cache's lock it serves the published version at that key, or, while another builds, rolls back (holding no reader), waits outside any transaction and starts again, or starts again when the published version is newer than its snapshot, or else becomes the account's one builder: it applies the changes since the published version (a full build only for a first build, another lineage or generation, or after a purge) in its own transaction, publishes the result only if the account's incarnation is still the one taken before its snapshot was pinned (so a generation change, restore or deletion meanwhile discards it) and the result is newer, and serves it. A response made from a library is sent only if the library's incarnation is still the account's once it is made (`Cache.Valid`; list pages: the registry's final check). An apply found inconsistent, a verified apply that differs from a full build, or two failed builds purge the account: a new incarnation (`Spool.Retire`), the version dropped, and the next 3 applies each verified; the first apply of each account after a start is verified too, and `POST /v1/admin/read-model/verify` verifies on demand, as a build of the election. Only a completed, matching verification of an apply in the current incarnation counts toward these checks. Memory is bounded by structure, per account: the published version, the one before it and at most 2 leased versions (those of the most recently read views read in the last 10 minutes, so a list held open survives a playing phone's checkpoints) while views pin them, the views of any other version expiring at publication; one build with its verification's full build; and one library per admitted response, at most 2 at once (`Spool.Admit`: pages being encoded and screens being made; a page read is admitted before its view is looked up, so a waiting read pins nothing). At most 8 accounts hold a library, counting released accounts whose responses are still being made (`Cache.enter`: a ninth account's read waits for one to end; no source in use is freed or invalidated); each is released with its views after 10 minutes unread or to make room. With sharing, the worst state an account reaches (both leases, both admitted responses on older versions, the previous and published versions, and a verified build with its full comparison build) measures about 2 libraries at 50,000 episodes when one-episode commits separate its versions (`TestCacheElectionAtScale`, `NTP_READMODEL_SCALE=1`, gated at 2.5). Broad commits (the whole library's played state) leave versions little to share: two leased lists then hold about 4 libraries and the worst state about 8, the structural bound (`TestCacheBroadChangesHeldState`, gated at 4.5 and 8.5; at 100,000 episodes with `NTP_READMODEL_SCALE=1`). A household's worst case is therefore up to 8 libraries per account holding one (PROTOCOL §14 gives the sizes). `Cache.Close` cancels and waits for every cache operation. Warmers (`Cache.StartWarmers`, started by `api.Server.WarmLibraries` with the startup warm-up of the accounts active in the last 30 days) advance a read account's version after each of its commits; correctness never depends on them.
- A list is a plan (`query.go`): the (podcast, class) ranges of one sort order's tree that its filter passes, over the shown podcasts (a podcast's own for its list), or the shown podcasts' queue ranges; its length comes from the podcasts' class counts, and its rows are the k-way merge of the ranges in the order's comparison (column, rank, ID). A page at any offset is found by multi-range selection, an anchor by its rank in each range; a page costs O(R log n + rows log R), a selection O(R log n log N) more, R being the ranges.
- The views registry (`spool.go`, in memory) keeps each list view's version, plan and a few cursors, never rows: pages are merged and encoded from the view's own version when read. A page is read only when the account's current identity (its log lineage and library generation, read by the request in two point reads) is the view's, and released only if the view is still live once encoded, so a purge (`Spool.Retire`, a new incarnation) or a new generation during a page expires it. Registration is fenced by the incarnation and by the newest identity seen, ordered within a log by epoch then generation: a slow request of an older identity neither registers a view nor expires newer ones. Identical first requests share a view.
- Counters, subscriptions, statistics, the podcast card and Home come from the podcasts' aggregates, the statistics prefix sums and the Continue and Surprise partitions (`screens.go`, `home.go`): O(P log n) and what they show. The media checks look up only their own episode or podcast.

Tests:

- `viewstest.Main`, in the `TestMain` of `internal/api`, `protocol`, `ops`, `refresh`, `importer`, `acceptancecheck`, `views` and (as the external `storage_test` package's) `storage`, installs a commit observer: per store and account it advances a version by each commit, in the commit's snapshot while the write gate keeps the next write out (read on a connection of its own, `storage.VerifyReadForTesting`, so that pool readers waiting on the write cannot block it), and compares it with a full build there, and both versions' identity (account, head, clock) with the snapshot's; a difference fails the test that committed, and a library neither builds is exempt only when the oracle cannot load it either. Each package's `TestReadModelObserverActive` fails without it.
- `internal/views/reference` is the oracle: the views' code before the read model, with its own copies of the SQL reads, frozen by `TestReferenceIsFrozen`. `TestTestSeamsStayInTests` keeps the oracle, the harness and the `…ForTesting` seams out of the server's import graph.
- `internal/views/queries_reference_test.go` (the query matrix) compares every list of the query matrix (35 filters × 11 orders over all podcasts and four, Inbox, Favourites, History, the queue, the subscription list's options), walked in pages of random sizes through the registry, and the other screens with the oracle byte for byte; `internal/api/readmodel_commits_test.go` (real commits over HTTP) imports a medium library for real (the parity backup copied to 128 podcasts and about 6,000 episodes) after the empty account's views were read, then makes real commits through HTTP and the server: every fact type that changes the library, refreshes with new, dropped and re-identified items, a podcast merge, unsubscribing and subscribing again, rebuilds in place and staged, a restore with the phone's recovery and another account's deletion. After every step pages of earlier views are read again (the same rows, or 410 once the account's lineage or generation changed) and the served responses are compared with the oracle's composition of the earlier handlers (`reference/api.go`); the first steps go through every kind until each changes the library, and a kind that never does fails the run (`NTP_READMODEL_SCALE=1`: the power user's library, about 50,000 episodes). `views_registry_test.go`, `views_fences_test.go`, `readmodel_fences_test.go` and `screens_budget_test.go` cover paging, anchors in every order and the queue, the registry's identity fence and final check, expiry, the screens' work budgets and a view's measured footprint.
- `internal/views/model_*_test.go`: the builders against the oracle on the Android fixtures, with the maintained queue, Continue and Surprise trees walked and compared with expectations derived from the frozen rules (`model_structures_test.go`), and `EqualVersions` against deliberately wrong versions; randomized commit sequences on a medium library (3 seeds × 1,000 steps) and a power user's (120 podcasts, 50,400 episodes, a 5,000-episode queue, ten years of history; 60 steps), each step compared with a full build and every 50th or 20th with the oracle (`NTP_READMODEL_SEED`, `NTP_READMODEL_STEPS`, `NTP_READMODEL_LONG=1` for ten times the steps, and `NTP_READMODEL_REPLAY` for a failed run's trace in `.work/readmodel-failures/`); work budgets against library, queue, history and payload size; and the change-page and batch boundaries. Under the race detector, as in `make check`, the sequences run a tenth of their steps and the single-goroutine tests at scale skip; [README](../README.md#development) gives the commands that run them in full and the opt-in power-user runs (`NTP_READMODEL_SCALE=1`).

## Test data

Every test input is synthetic, generated by the project, copied unchanged from AntennaPod (GPL-3.0) or produced by AntennaPod's own code.

- `contract/vectors/`: the shared vectors ([CONTRACT.md](CONTRACT.md)). `contract/vectors/feeds/` holds the feed parser corpus and the outputs of Android AntennaPod 3.12.1's own parser for it; its `PROVENANCE.md` is written by `contract/reference/gen_feed_corpus.py` with the corpus and copied with it into the client repositories, so it stays beside the files it describes.
- `internal/importer/androiddb/testdata/`: Android backup fixtures copied from NotTennaPod-iOS `TestSupport/Data/database-restore/` (synthetic test libraries; feeds point at local fixture servers or `example.invalid`):
  - `android-3.12.1/`: libraries made by AntennaPod 3.12.1 on the Android emulator.
  - `older-versions/`: backups generated from the table definitions of older AntennaPod releases (`PodDBAdapter` at the release named in each file name, 0.8 to 3.8.0), and `v3110000-edges.db`, edge values in the 3.12.1 schema.
  - `android-3.12.1-upgraded/`: the same older files after AntennaPod 3.12.1 itself upgraded them (the oracle for the ported upgrader).
  - `invalid/`: files the import must refuse (NotTennaPod-iOS's `invalid/invalid.json` records what Android does with each).
- `internal/importer/testdata/opml/`: OPML documents and `oracle.json`, unchanged copies from NotTennaPod-iOS `Tests/NotTennaPodCoreTests/Fixtures/OPMLFixtures/`, where AntennaPod's unchanged reader with Android's own KXmlParser produced the oracle. Only the documents of the cases the test reads (scope `supported`) and `prefix-before-root.opml` are copied; the oracle also lists the other pending cases, whose documents stay in NotTennaPod-iOS.
- `internal/feed/testdata/discovery/`: the feed discovery pages, unchanged copies of NotTennaPod-iOS `TestSupport/Data/add-podcast-discovery/pages/`; `expected.json` takes their outcomes from that repository's `expected/discovery.json` (its `_comment` says how).
- `internal/feed/testdata/dates_golden.json`: the date parser's golden corpus, generated by this server's parser from a fixed seed (its header says how). NotTennaPod-iOS keeps an unchanged copy as `Tests/NotTennaPodCoreTests/Fixtures/ParityDatesGolden.json`, and NotTennaPod-Web keeps unchanged copies of `contract/vectors/queue_*.json` in `test/vectors/`.
- The read model's libraries (`internal/views/viewstest`) are generated by the tests from fixed seeds (synthetic titles, `example.invalid` addresses) and written through the storage writers; nothing is stored in the repository.
